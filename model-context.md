# Calendar Collab - Model Context and Requirements

This document summarizes the key requirements, constraints, and lessons learned while creating the `calendar-collab` application using Liferay Objects.

## Overview

The `calendar-collab` app is a recreation of the existing Liferay Calendar app using:
- **Backend**: Liferay Objects (instead of Service Builder)
- **Frontend**: Modern React/TypeScript with Clay UI components (instead of JSP)
- **Testing**: Playwright test suite following existing patterns

## Object Definition Requirements

### System vs Custom Objects

**Critical Constraint**: Custom objects must be marked as `"system": false`. System objects are reserved for Liferay core functionality.

- ✅ **Correct**: `"system": false` for custom objects
- ❌ **Incorrect**: `"system": true` for custom objects (causes "Forbidden modifiable system object definition name" error)

### External Reference Code Prefixes

**Critical Constraint**: The `L_` prefix is reserved for system objects only. Custom objects must use a different prefix.

- ✅ **Correct**: `"externalReferenceCode": "C_CALENDAR_COLLAB_RESOURCE"` (using `C_` prefix)
- ❌ **Incorrect**: `"externalReferenceCode": "L_CALENDAR_COLLAB_RESOURCE"` (causes "The prefix L_ is reserved" error)

**Note**: All relationship references (`objectDefinitionExternalReferenceCode1` and `objectDefinitionExternalReferenceCode2`) must also use the correct prefix.

### Relationship Type Enum Values

**Critical Constraint**: The `ObjectRelationship.Type` enum only supports specific values.

**Supported Types**:
- `"oneToMany"` - One object to many related objects
- `"oneToOne"` - One object to one related object
- `"manyToMany"` - Many objects to many related objects

- ✅ **Correct**: `"type": "oneToMany"`
- ❌ **Incorrect**: `"type": "manyToOne"` (not a valid enum value)

**Note**: When defining a `oneToMany` relationship, it should be defined from the perspective of the "one" side. For example, if Resource has many Calendars, define the relationship in Resource's `objectRelationships` array.

### Relationship System Flag

**Critical Constraint**: Custom object relationships must be marked as `"system": false`. Only system bundles can create system relationships.

- ✅ **Correct**: `"system": false` for custom relationships
- ❌ **Incorrect**: `"system": true` for custom relationships (causes "Only allowed bundles can add system object relationships" error)

### Relationship Name Length

**Critical Constraint**: Relationship names must be less than 41 characters.

- ✅ **Correct**: `"name": "resourceToCalendar"` (18 characters)
- ❌ **Incorrect**: `"name": "calendarCollabResourceToCalendarCollabCalendar"` (45 characters - causes "Name must be less than 41 characters" error)

**Best Practice**: Use shortened, descriptive names:
- `resourceToCalendar` instead of `calendarCollabResourceToCalendarCollabCalendar`
- `calendarToEvent` instead of `calendarCollabCalendarToCalendarCollabEvent`
- `eventToParentEvent` instead of `calendarCollabEventToParentEvent`

### Localized Fields Cannot Be Required

**Critical Constraint**: Fields with `"localized": true` cannot have `"required": true`.

- ✅ **Correct**: `"localized": true, "required": false`
- ❌ **Incorrect**: `"localized": true, "required": true` (causes "Localized object fields must not be required" error)

**Reason**: Localized fields store values per locale, so they cannot be required at the object level.

## Module Structure

### Module Naming Conventions

Following Liferay's module naming conventions:

- **Implementation Module**: `calendar-collab-impl`
  - Location: `modules/apps/calendar-collab/calendar-collab-impl/`
  - Contains: Object definitions (batch engine data JSON files)
  
- **REST API Module**: `calendar-collab-rest-api`
  - Location: `modules/apps/calendar-collab/calendar-collab-rest-api/`
  - Contains: DTOs and resource interfaces (generated by REST Builder)
  
- **REST Implementation Module**: `calendar-collab-rest-impl`
  - Location: `modules/apps/calendar-collab/calendar-collab-rest-impl/`
  - Contains: REST endpoint implementations and OpenAPI spec
  
- **Web Module**: `calendar-collab-web`
  - Location: `modules/apps/calendar-collab/calendar-collab-web/`
  - Contains: React/TypeScript frontend components

### Batch Engine Data Location

Object definitions are deployed via batch engine data files:

- **Path**: `modules/apps/calendar-collab/calendar-collab-impl/src/main/resources/com/liferay/calendar/collab/internal/batch/`
- **File Pattern**: `{number}-{description}.batch-engine-data.json`
- **Example**: `01-object-definition.batch-engine-data.json`

### Batch Engine Configuration

The `bnd.bnd` file must include:

```
Liferay-Client-Extension-Batch: com/liferay/calendar/collab/internal/batch
```

This tells Liferay where to find the batch engine data files.

## Object Definition Structure

### Required Fields

Each object definition must include:

```json
{
  "externalReferenceCode": "C_{OBJECT_NAME}",
  "label": {
    "en_US": "Human Readable Name"
  },
  "name": "ObjectName",
  "modifiable": true,
  "system": false,
  "scope": "company",
  "objectFields": [...],
  "objectRelationships": [...]
}
```

### Field Types

Common field types used:
- `"type": "String"` - Text fields
- `"type": "Clob"` - Long text fields (descriptions)
- `"type": "Long"` - Integer fields
- `"type": "Boolean"` - Boolean fields
- `"type": "DateTime"` - Date/time fields

### Relationship Structure

```json
{
  "deletionType": "prevent" | "cascade",
  "externalReferenceCode": "C_{RELATIONSHIP_NAME}",
  "label": {
    "en_US": "Human Readable Relationship Name"
  },
  "name": "shortRelationshipName",  // Must be < 41 characters
  "objectDefinitionExternalReferenceCode1": "C_{OBJECT1}",
  "objectDefinitionExternalReferenceCode2": "C_{OBJECT2}",
  "objectDefinitionSystem2": false,
  "system": false,
  "type": "oneToMany" | "oneToOne" | "manyToMany"
}
```

## Deployment Process

### Build and Deploy

1. Build the module:
   ```bash
   cd modules/apps/calendar-collab
   ../../../gradlew :apps:calendar-collab:calendar-collab-impl:build
   ```

2. Deploy the module:
   ```bash
   ../../../gradlew :apps:calendar-collab:calendar-collab-impl:deploy
   ```

3. Check logs for batch engine import:
   ```bash
   tail -f /opt/dev/projects/github/bundles/logs/liferay.2025-11-21.log | grep -i "batch\|error"
   ```

### Common Deployment Errors and Fixes

1. **"Invalid enum value: manyToOne"**
   - **Fix**: Change `"type": "manyToOne"` to `"type": "oneToMany"`

2. **"Forbidden modifiable system object definition name"**
   - **Fix**: Set `"system": false` for all object definitions

3. **"The prefix L_ is reserved"**
   - **Fix**: Change all `L_` prefixes to `C_` (or another non-reserved prefix)

4. **"Localized object fields must not be required"**
   - **Fix**: Set `"required": false` for all fields with `"localized": true`

5. **"Only allowed bundles can add system object relationships"**
   - **Fix**: Set `"system": false` for all relationships

6. **"Name must be less than 41 characters"**
   - **Fix**: Shorten relationship names (e.g., `resourceToCalendar` instead of `calendarCollabResourceToCalendarCollabCalendar`)

## Auto-Generated REST Endpoints

Liferay Objects automatically generates CRUD REST endpoints for each object definition:

- **Base Path**: `/o/c/{object-name-lowercase}`
- **Example**: `/o/c/calendarcollabresources` for `CalendarCollabResource`
- **Endpoints**:
  - `GET /o/c/{object-name}` - List objects
  - `GET /o/c/{object-name}/{id}` - Get single object
  - `POST /o/c/{object-name}` - Create object
  - `PUT /o/c/{object-name}/{id}` - Update object
  - `DELETE /o/c/{object-name}/{id}` - Delete object

## REST Builder for Custom Endpoints

For custom REST endpoints beyond CRUD operations:

1. **OpenAPI Specification**: Define endpoints in `rest-openapi.yaml`
2. **REST Config**: Configure REST Builder in `rest-config.yaml`
3. **Build Plugin**: Apply `com.liferay.portal.tools.rest.builder` plugin in `build.gradle`
4. **Generation**: REST Builder generates DTOs and resource interfaces automatically

## Key Learnings

1. **Always use `system: false`** for custom objects and relationships
2. **Never use `L_` prefix** for custom object external reference codes
3. **Keep relationship names short** (< 41 characters)
4. **Localized fields cannot be required** - use validation at the application level instead
5. **Relationship types are limited** - only `oneToMany`, `oneToOne`, and `manyToMany` are supported
6. **Batch engine data files** are automatically processed when the bundle is deployed
7. **Check logs immediately after deployment** to catch validation errors early
